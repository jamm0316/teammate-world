# ADR-012: 운세(사주·타로) 전송 계약 — REST + 서버 풀이

- 상태: 확정
- 날짜: 2026-07
- 분류: [기획+백엔드]

## 문제(Context)
월드 '🔮 운세존'의 점술가 NPC가 사주·타로 풀이를 제공한다. 프론트는 POC 데모(로컬 풀이)로 먼저 구현했고, 서버 연동 시 ① 어떤 프로토콜로 보낼지 ② 타로 카드 셔플·선택을 누가 권위로 가질지 ③ 풀이 텍스트를 어디서 만들지 결정해야 한다.

## 대안(Options)
- 전송: (a) WS(STOMP) publish — 종목과 동일한 경로 / (b) REST POST — 요청·응답 1:1
- 셔플 권위: (c) 클라 셔플 후 뽑은 카드 번호만 전송 / (d) 서버가 덱을 섞어 내려주고 클라는 인덱스만 전송
- 풀이 생성: (e) 클라가 카드·간지 → 텍스트 매핑 보유 / (f) 서버가 텍스트까지 완성해 내려줌

## 결정(Decision)
**(b) REST + (c) 클라 셔플 + (f) 서버 풀이**로 간다. 계약은 아래로 고정한다.

| 경로 | 전송 | 요청 | 응답 |
|---|---|---|---|
| 사주 풀이 | REST `POST /api/fortune/saju` | `{name, birthDate, hourBranch}` | 사주 8자 + 오행 분포 + 섹션별 풀이 |
| 타로 풀이 | REST `POST /api/fortune/tarot` | `{category, cards:[n,n,n]}` | 위치별 카드 해석 + 종합 풀이 |

요청 필드
- `birthDate` — `YYYY-MM-DD` (양력). 음력 입력은 이번 범위에서 제외한다.
- `hourBranch` — 12지지 한 글자(`자`~`해`) 또는 `null`(시간모름). `null`이면 시주(時柱)를 비운 채 풀이한다.
- `category` — `love` | `money` | `work` | `health`
- `cards` — 메이저 아르카나 번호 0~21 중 서로 다른 3개. **배열 순서가 곧 과거·현재·미래 스프레드 위치**다.

응답 스키마는 프론트의 `demoSaju()` / `demoTarot()` 반환값과 동일하게 맞춰 두었다(`frontend/fortune.js`). 연동은 그 두 함수 호출을 `fetch`로 교체하는 것으로 끝난다.

## 근거(Rationale)
① 운세 풀이는 요청–응답이 1:1이고 다른 참가자에게 전파할 필요가 없다. ADR-011의 판별식("실시간·다자 전파 → WS, 그 외 → REST")상 REST 경로다. 종목처럼 WS로 보내면 응답을 개인 큐로 되돌려 받는 상관관계 처리가 순이익 없이 늘어난다.
② 셔플을 클라가 갖는 이유: 이 기능에는 승패·보상이 걸려 있지 않아 조작 유인이 없고, 서버 셔플로 만들면 "덱 내려받기 → 선택 전송"의 왕복이 하나 더 붙어 카드 펼침 연출이 네트워크에 묶인다. **단, 결과에 칭호·보상을 걸게 되면 이 결정은 뒤집어야 한다** — 그 순간 셔플은 ADR-006과 같은 이유로 서버 권위가 된다.
③ 풀이 텍스트를 서버가 만드는 이유: 22장 × 4카테고리 문구와 사주 풀이 풀이 클라에 있으면 문구 수정마다 배포가 필요하고, 캐시된 PWA에서는 갱신이 더 늦다. 또한 LLM 기반 풀이로 확장할 여지를 남긴다.
④ 사주 계산 위치: 년주·월주·시주는 간지 규칙만으로 나와 클라에서도 정확하지만, **일주는 만세력 테이블이 필요**해 서버 몫이다. 절기 경계(입춘·월건)와 진태양시 보정도 같은 이유로 서버에서 처리한다.

## 결과(Consequences)
- 사주 입력값은 개인정보(생년월일)다. 저장하지 않고 요청–응답 안에서만 쓰는 것을 기본으로 하고, 이력 기능을 붙일 때 별도 동의 절차를 설계한다.
- POC 데모의 일주는 해시 기반 임시값이라 결과 화면에 데모 표기를 남겼다. 서버 연동 시 표기와 함께 제거한다.
- 프론트 연동 지점은 `[MX]` 주석으로 표기했다 (`grep -rn "\[MX\]" frontend/fortune.js`).
- 타로 결과는 `(category, cards)`가 같으면 항상 같아야 한다. 서버가 LLM을 쓰더라도 이 결정성은 캐시로 유지한다.

## 표준 어휘(Translation)
request–response over REST; client-side shuffle with server-side interpretation; deterministic reading per (category, spread)
